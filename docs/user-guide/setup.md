# Setup

Choose the backend before configuring QDash: Fake runs without quantum hardware, while Qubex
connects QDash to a supported lab system.

## Choose a Backend

| Goal | Setup path |
| --- | --- |
| Evaluate QDash without quantum hardware | [Fake backend](./setup/fake-backend.md) |
| Operate a Qubex-connected lab deployment | [Qubex backend](./setup/qubex-backend.md) |
| Connect another hardware stack | Under construction — the current release accepts only `fake` and `qubex`; another backend requires QDash code changes, not deployment settings. |

Both supported paths use the same Docker Compose stack. The backend choice changes the available
calibration tasks and whether the workflow worker opens a hardware connection.

Host-side API and UI processes are a development workflow. Use
[Development Environment Setup](../developer-guide/setup.md) instead of this page when changing
QDash code.

## Prepare the Host

Install Git, Docker, and Docker Compose v2.24.4 or later. Go Task is optional; every required
setup command has a Docker Compose equivalent.

Clone the stable branch. The repository default is `develop`, so select `main` explicitly:

```bash
git clone --branch main https://github.com/oqtopus-team/qdash.git
cd qdash
```

The `main` branch contains stable releases. Do not use `develop`, a feature branch, or a
prerelease tag for an operational installation. Follow [System Updates](./system-updates.md) to
move an existing installation to another release.

Next, complete either the [Fake backend](./setup/fake-backend.md) or
[Qubex backend](./setup/qubex-backend.md) configuration. Each path creates the `.env` file used by
the remaining steps.

## Configure Shared Deployment Settings

Set a unique initial administrator password in `.env` before exposing QDash to a network.

| Variable | Purpose |
| --- | --- |
| `QDASH_ADMIN_USERNAME` / `QDASH_ADMIN_PASSWORD` | Initial administrator login |
| `UI_PORT` | Host port for the Caddy entry point in HTTP mode; defaults to `5714` |
| `MONGO_DATA_PATH` / `POSTGRES_DATA_PATH` | Persistent database directories |
| `CALIB_DATA_PATH` | Calibration figures, raw data, and run artifacts |
| `CLIENT_URL` | Public origin used in links generated by QDash |
| `NEXT_PUBLIC_DEFAULT_THEME` | Initial UI theme for browsers without a saved preference |

The example files also list internal service ports and optional AI provider, Slack, knowledge
repository, and tunnel settings. The normal Compose stack does not publish internal service
ports. Leave an optional credential empty when that integration is not in use.
Set `CLIENT_URL` to an HTTP or HTTPS origin with a host and optional port, without a path. QDash
removes a trailing slash. When it is unset, generated links use `http://localhost:<UI_PORT>`.

### Configure AI

The AI runtime and its workspace start with the standard Compose stack. Internal authentication
is generated automatically; no AI service profile or UI enable flag is required.

Set the `OPENAI_COMPATIBLE_BASE_URL_CHAT` and `OPENAI_COMPATIBLE_API_KEY_CHAT` pair in `.env`
for chat, and the corresponding `EVALUATION` pair for figure analysis. Base URLs must include
`/v1`. Select models in `config/copilot/chat.yaml` and `config/copilot/evaluation.yaml`.

Copilot can propose supported write operations without an extra enable setting. The signed-in
user must approve each proposed write in the chat, and their project permissions still apply.
The retired `AGENT_RUNTIME_ENABLE_WRITE_TOOLS` variable has no effect and can be removed from
existing `.env` files.

#### Authenticate AI endpoints with Cloudflare Access

Use one Cloudflare Access service token for chat and figure analysis. Create the token and add it
to a **Service Auth** policy on each AI endpoint's Access application, following
[Cloudflare's service token instructions](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/).

Set the shared credentials in `.env`:

```dotenv
CF_ACCESS_CLIENT_ID=<service-token-client-id>
CF_ACCESS_CLIENT_SECRET=<service-token-client-secret>
```

Keep the existing `OPENAI_COMPATIBLE_BASE_URL_CHAT` and `OPENAI_COMPATIBLE_BASE_URL_EVALUATION`
settings pointed at the protected HTTPS URLs, including `/v1`. The shared token is sent to every
endpoint configured through `base_url: env:OPENAI_COMPATIBLE_BASE_URL_<SUFFIX>`, including custom
suffixes. Literal URLs and built-in providers do not receive it.

Keep each endpoint's API key if the model server requires it. If authentication is handled only
by Cloudflare Access, leave that API key empty. Both Access values must be set together; leave
both empty to keep using API-key-only authentication.

After changing `.env`, recreate the runtime to load the values:

```bash
docker compose up -d --build --force-recreate agent-runtime
```

### Set the Default Color Theme

Set `NEXT_PUBLIC_DEFAULT_THEME` to `light`, `dark`, `cupcake`, `emerald`, `corporate`,
`synthwave`, `nord`, `night`, `dracula`, `dim`, `abyss`, `business`, `coffee`, or `sunset`.
An unsupported value falls back to `light`.

A theme selected from **Settings** is saved in the browser and takes precedence. This variable is
embedded in the UI image at build time; rebuild the UI after changing it:

```bash
docker compose build ui
docker compose up -d ui
```

## Start QDash

Validate the resolved Compose configuration, then build and start the enabled services:

```bash
docker compose config --quiet
docker compose up -d --build
```

If Go Task is installed, `task deploy-local` performs the startup and also pulls the optional
knowledge repository configured by `KNOWLEDGE_REPO_URL`.

Application logs use Docker named volumes. The Pi runtime stores resumable conversation state in
the `agent-runtime-state` volume. Normal container recreation preserves both.

## Verify the Installation

Confirm that the containers are running:

```bash
docker compose ps
```

Open QDash through the Caddy entry point:

- QDash UI: <http://localhost:5714/login>
- API documentation: <http://localhost:5714/api/docs>
- Prefect dashboard: <http://localhost:5714/prefect/dashboard>

Replace port `5714` in these addresses if `UI_PORT` has a different value.

Sign in with `QDASH_ADMIN_USERNAME` and `QDASH_ADMIN_PASSWORD`. Prefect uses the same QDash
sign-in. Any signed-in QDash user can see orchestration state across projects in Prefect; QDash
project permissions do not limit Prefect's view. Use QDash for workflow changes so its project
metadata stays synchronized. For a Fake deployment, continue with
[Running Calibrations](./running-calibrations.md). For Qubex, confirm the intended chip and
hardware configuration before starting a task.

## Serve QDash over HTTPS

Use Caddy to terminate HTTPS for a public domain. Point the domain's DNS records at the host and
allow inbound TCP ports 80 and 443 through its network firewall. Caddy obtains and renews the
certificate; its `caddy-data` and `caddy-config` volumes keep certificate and configuration state
across container recreation.

Set `CLIENT_URL` to the public origin, then validate and start the same Compose files together:

```dotenv
CLIENT_URL=https://qdash.example.com
```

```bash
docker compose -f compose.yaml -f compose.https.yaml config --quiet
docker compose -f compose.yaml -f compose.https.yaml up -d --build
```

The HTTPS override publishes TCP ports 80 and 443 instead of the default HTTP port. Open the
origin in `CLIENT_URL` to verify the installation. With this override, `CLIENT_URL` must use
HTTPS with the default port (omit the port or specify `:443`); a custom port cannot work because
the override publishes only 80 and 443. A single trailing slash is normalized away.

Stop the direct HTTPS stack with the same file list so Compose targets the same project
configuration:

```bash
docker compose -f compose.yaml -f compose.https.yaml down
```

For CLI development or a separate TLS terminator that uses a custom public port, keep the regular
HTTP Compose configuration and set `CLIENT_URL` to the public origin, including that port. A
front TLS terminator must be listed in `CADDY_TRUSTED_PROXIES`.

For an EC2 host, configure DNS and inbound network rules outside this repository; QDash does not
provision AWS resources. Keep `CLIENT_URL` set to the public HTTPS origin so generated links use
the address users open in their browsers.

## Enable Remote Access

Set `CLIENT_URL` to the public HTTPS origin, set `TUNNEL_TOKEN`, and enable the `tunnel` Compose
profile. Configure the Cloudflare Tunnel public hostname to use the Caddy host entry at
`http://localhost:${UI_PORT:-5714}` (or the configured Caddy host port). Do not point the tunnel
directly at the UI, API, or Prefect service; Caddy remains the only browser ingress.

Set `CADDY_TRUSTED_PROXIES` to the source IP or smallest CIDR that Caddy actually sees for
connections from `cloudflared`. Check the peer address using the host or container network
diagnostics; Docker may present the bridge gateway instead of `127.0.0.1`. Keep the loopback
default only when that is the observed peer, and do not trust an entire Docker subnet or other
broad network.

```dotenv
CLIENT_URL=https://qdash.example.com
TUNNEL_TOKEN=<cloudflare-tunnel-token>
COMPOSE_PROFILES=tunnel
CADDY_TRUSTED_PROXIES=<tunnel-peer-ip-or-cidr>
```

Start the stack again with `docker compose up -d --build`. `task deploy` is the equivalent Go
Task command; it enables the tunnel while preserving profiles already configured in `.env`.

## Migrate Existing Settings

Remove `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_PREFECT_URL` from `.env`; browser API requests now
use the same-origin `/api` path and the Prefect link uses `/prefect/dashboard`. The example files
leave `PREFECT_API_URL` blank so `task dev-api-local` selects the correct address for its
environment: `http://127.0.0.1:${PREFECT_PORT:-4200}/prefect/api` on the host and
`http://prefect-server:4200/prefect/api` in a DevContainer. Compose API, worker, and deployment
services use the internal service address. If an existing `.env` sets `PREFECT_API_URL`
explicitly, change its path from `/api` to `/prefect/api` and use the host or container address
appropriate to that process. Rebuild the UI image after removing the old public URL settings:

```bash
docker compose up -d --build ui
```

Review any local `compose.override.yaml` for old API, UI, Prefect, database, or deployment-service
port mappings. Remove mappings you no longer need, then inspect the resolved configuration with
`docker compose config` before starting the stack. Existing override files remain active even
after the base Compose file stops publishing those ports.
